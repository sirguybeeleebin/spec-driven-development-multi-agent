# Компоненты движка

Движок состоит из компонентов, отвечающих за взаимодействие с LLM, выполнение AI-агентов, обработку отдельных задач и координацию выполнения рабочего процесса.

## 1. Tool

`Tool` — контракт инструмента, который AI-агент может вызывать во время взаимодействия с LLM.

Определяет два метода:

- `get_openai_schema()` — возвращает описание инструмента в формате OpenAI Function Calling.
- `execute(args)` — выполняет инструмент с переданными аргументами и возвращает результат.

## Guardrails

`Guardrails` — компоненты, обеспечивающие соблюдение ограничений и правил безопасности при выполнении инструментов AI-агентами.

Предохранители проверяют вызовы инструментов перед их выполнением и предотвращают операции, нарушающие установленные ограничения проекта или правила работы движка.

Каждый предохранитель реализует общий контракт `Guardrail` с методом `check()`, который получает объект `State` и текущий `ToolCall`.

Метод `check()`:

- Проверяет соответствие вызова инструмента установленным ограничениям.
- Завершается без исключения, если вызов разрешён.
- Выбрасывает исключение `ValueError`, если вызов нарушает ограничения.

`Agent` получает список предохранителей через конструктор. Перед выполнением каждого вызова инструмента последовательно запускает все предохранители. Если хотя бы один предохранитель обнаруживает нарушение, выполнение инструмента отменяется, а информация об ошибке добавляется в историю сообщений как результат вызова инструмента. После этого цикл взаимодействия с LLM продолжается.

В движке предусмотрены следующие предохранители:

1. **FQNWriteGuardrail** — контролирует операции записи в файлы. Проверяет, что инструменты записи (`append_file`, `patch_file`) изменяют только файл, назначенный текущему интерфейсу через `state.current_target_file`. Отклоняет операции записи, если целевой файл не установлен или путь записи не совпадает с ожидаемым.

2. **BashGuardrail** — ограничивает использование Bash исключительно чтением файлов проекта и выполнением тестов. Запрещает команды создания, изменения и удаления файлов и директорий, перенаправление вывода в файлы, загрузку файлов с параметрами сохранения, а также другие операции, способные изменить содержимое проекта.

Таким образом, `Guardrails` обеспечивают дополнительный уровень контроля над действиями AI-агентов, ограничивая использование инструментов установленными правилами и предотвращая несанкционированное изменение файлов проекта.

## 2. LLMClient

`LLMClient` — контракт клиента для взаимодействия с LLM.

Метод `complete()` принимает:
- `messages` — историю сообщений диалога.
- `tools` — доступные инструменты.

Возвращает:
- `Message` — ответ модели.
- `list[Metric]` — метрики выполнения запроса.

## 3. PromptProvider

`PromptProvider` — контракт поставщика промптов для AI-агента.

Определяет:

- `system` — системный промпт агента.
- `format_user(state, skills)` — формирует пользовательский промпт на основе текущего состояния и доступных навыков.
- `final_user` — финальный промпт, запрашивающий итоговый результат работы агента.
- `parse_final_response(final_response)` — преобразует финальный ответ LLM в структурированный результат.

Для каждого типа агента используется собственная реализация `PromptProvider`, определяющая его инструкции и формат контекста.

## 4. Agent

`Agent` — компонент, реализующий полный цикл работы одного AI-агента: взаимодействие с LLM, выполнение инструментов и формирование итогового результата.

Получает через конструктор:

- `llm` — клиент для взаимодействия с LLM.
- `prompt_provider` — поставщик промптов.
- `skills` — доступные навыки.
- `tools` — доступные инструменты.
- `guardrails` — набор проверок, выполняемых перед запуском инструментов.
- `max_iterations` — максимальное количество итераций взаимодействия с LLM.

Метод `run(state)`:

1. Формирует начальную историю сообщений из системного и пользовательского промптов.
2. Запускает цикл взаимодействия с LLM, передавая ей историю сообщений и доступные инструменты.
3. Добавляет ответы LLM в историю сообщений.
4. Если ответ содержит вызовы инструментов, находит соответствующие инструменты, выполняет проверки `Guardrails` и запускает инструменты.
5. Добавляет результаты выполнения инструментов в историю сообщений.
6. Повторяет взаимодействие с LLM до получения ответа без вызовов инструментов или достижения `max_iterations`.
7. Добавляет финальный пользовательский промпт и выполняет заключительный вызов LLM без доступных инструментов.
8. Извлекает финальный ответ и преобразует его с помощью `PromptProvider.parse_final_response()`.

Возвращает `AgentResult`, содержащий структурированный результат работы агента, историю сообщений и метрики всех вызовов LLM.

## 5. TaskRunner

`TaskRunner` — компонент, координирующий работу AI-агентов в рамках одной задачи разработки.

Получает через конструктор четыре агента:
- `Researcher` — исследование задачи и технических решений.
- `Implementer` — реализация интерфейсов.
- `Tester` — проверка реализации по сценариям приёмки.
- `Fixer` — исправление ошибок, обнаруженных при тестировании.

Метод `run(task)`:

1. Создаёт объект `State` для текущей задачи.
2. Запускает `Researcher` и сохраняет результат в `state.agent_results`.
3. Последовательно обрабатывает все интерфейсы задачи:
   - Устанавливает `state.current_interface`.
   - Запускает `Implementer`.
   - Сохраняет результат работы агента.
4. Сбрасывает `state.current_interface`.
5. Последовательно обрабатывает все сценарии приёмки:
   - Устанавливает `state.current_gherkin`.
   - Запускает `Tester`.
   - Сохраняет результат тестирования.
   - Если статус тестирования не `PASSED`, запускает `Fixer` и сохраняет его результат.
6. Сбрасывает `state.current_gherkin`.
7. Собирает результаты работы всех агентов и возвращает `TaskResult`.

## 6. WorkflowRunner

`WorkflowRunner` — компонент, координирующий выполнение набора задач в соответствии с графом зависимостей рабочего процесса.

Получает через конструктор:
- `task_runner` — исполнитель отдельной задачи.

Метод `run(workflow)`:

1. Инициализирует статус каждой задачи значением `IDLE`.
2. Строит список зависимостей каждой задачи на основе рёбер графа.
3. Определяет задачи, готовые к выполнению: все их зависимости должны иметь статус `SUCCESS`.
4. Если хотя бы одна зависимость завершилась со статусом `ERROR` или `HOLD`, задача получает статус `HOLD`.
5. Для каждой готовой задачи:
   - Устанавливает статус `RUNNING`.
   - Запускает `TaskRunner`.
   - При успешном выполнении устанавливает `SUCCESS` и сохраняет `TaskResult`.
   - При возникновении исключения устанавливает `ERROR`.
6. Повторяет определение готовых задач до завершения обработки рабочего процесса.

Возвращает `WorkflowResult`, содержащий результаты выполненных задач и итоговые статусы всех задач.
